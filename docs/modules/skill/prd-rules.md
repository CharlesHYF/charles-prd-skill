# PRD 规范模块划分
> 模块职责：定义规则模块各自管什么、校验器与内容评审的分工，模板、产品形态与仓库自检的约定，以及四种工作模式、两轮提问、等宽标注图与原型复刻的设计
> 负责人：Charles
> 系统模块：skill
> 关联文件：skills/*/SKILL.md、skills/charles-prd-standards/rules/、tools/check.sh、tools/capture.mjs、tools/annotate.mjs、templates/、tests/

## 功能一：规则模块边界

### 功能描述
规范本体按关注点拆成下列模块，每条规则只活在一个模块里。

| 模块 | 管什么 | 不管什么 |
| --- | --- | --- |
| structure | 目录结构、文件职责、prd.md 固定章节、字段定义、需求编号、多仓库场景 | 版本之间的关系 |
| versioning | 版本命名、major 与 minor、冻结规则、Git 对应 | 单个版本内部的文件 |
| prototype | 原型形态、按产品形态的界面覆盖表、截图工具契约、规范豁免、时效性 | 图的画法 |
| diagrams | Mermaid 图的类型与尺寸、界面标注图的截图与标注流程、外部位图来源 | 原型本身的内容 |
| boundaries | 产品文档与实现文档的信息落点、Release Criteria 与工程标准的分界 | 实现侧的任何规则 |
| tasks | 任务编号、六个固定小节、交互规格七字段、流程图要求 | 需求条目本身 |
| writing | 需求句式、可判定性、禁用表达、未确认数值的就地标注 | 文档结构 |
| export | 导出 PDF 的单向关系、两份文档的对外范围、交付记录 | 排版样式细节 |
| collaboration | 工作节奏、分析输出格式、产品取舍的处理 | 文档内容本身 |
| one-shot | 一键出全部的统一流程：先问后写、状态自检、一次产出、自检与交付说明 | 各模式自己的产物清单 |

### 入参要求
- 新增规则前先判定归属模块，避免同一条规则出现在多处
- 涉及实现侧的规则不写进本仓，写成通用表述交给使用者的项目决定
- 字段定义的 SQL 类型与主键策略是例外：字段表是建表的直接依据，属于产品侧有意规定的内容，写在 structure

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 规则内容 | 文本 | 是 | 待归入的规范条目 |
| 是否可机器校验 | 布尔 | 是 | 决定进 check.sh 还是进评审清单 |

### 返回
- 规则归入唯一模块
- 可校验的规则同时具备 check.sh 检查项与回归测试断言

## 功能二：校验器与评审的分工

### 功能描述
确定性规则由 `tools/check.sh` 拦，内容级矛盾由 `charles-prd-review` 的评审清单人工过。两者不重叠。文档里不写两边的条目数量，以 `check.sh` 的输出与评审清单本身为准。

| 校验器管 | 评审管 |
| --- | --- |
| 必需文件、版本目录命名、版本内必需文档 | 需求之间的矛盾 |
| prd.md 章节完整性与字段类型 | 范围与目标对不上 |
| 需求编号存在且不重复 | Non-goals 与需求冲突 |
| 图的位置与来源 | Release Criteria 无法判定 |
| 界面标注图的截图、坐标、标记块与坐标时效 | 需求编号的引用完整性 |
| 版本状态声明 | 原型与 PRD 不一致，含原型没有覆盖所选形态的界面类型 |
| 任务编号、小节、流程图、交互规格字段、已定义任务不留 data-todo | 文字表达无法判定 |
| 角色交叉引用 | 未解决问题的阻塞性 |
| `[待填]` 残留（功能四） | 需求确认记录逐条对账（功能八） |
| 产品形态声明、截图视口与移动端配对（功能五） | 真实页面与复刻原型并排核对（功能十） |
| 需求确认记录存在且有内容（功能八） | |
| 标注图高宽比、按钮与输入控件标注覆盖、界面小节必有标记块、标记块外不许手画 SVG（功能九） | |
| 原型页面来源对照表（功能十） | |

### 入参要求
- 新增检查项时同步更新 `tests/run_tests.sh` 的场景
- 发现某类内容问题反复出现且规则确定时，考虑从评审清单升格为检查项

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| PRD 根目录 | 路径 | 是 | 校验器的扫描范围，缺省 docs/prd |

### 返回
- 结构问题由脚本给出文件与具体位置
- 内容问题由评审按问题描述、存在的隐患、解决方案三段输出

## 功能三：模板与样例

### 功能描述
模板拆成两个目录，一个用来复制，一个用来参照。

| 目录 | 用途 | 内容 |
| --- | --- | --- |
| `templates/prd-template/` | 新产品与新版本的复制起点 | 只有结构与填写说明，所有要填的位置用 `[待填]` 前缀；原型是带截图 hook 的最小壳；不含 diagrams 产物；`notes.md` 固定带"需求确认记录"一节 |
| `templates/prd-example/` | 写法参照，不复制 | 订单系统的完整文档、原型、截图与标注，产品形态为后台管理系统、移动端适配为否 |

- 骨架原型只有一个空页面：状态切换条（Empty / Loading / Success / Error）、角色下拉、四个状态区块，满足 `capture.mjs` 的 hook 契约，不含任何业务内容
- 样例由原 `templates/export/sample-prd.md` 与 `sample-tasks.md` 拆回 `product.md`、`prd.md`、`scope.md`、`tasks.md`，原型与标注沿用现有订单系统
- 样张 PDF（`templates/export/sample-prd.pdf`、`sample-tasks.pdf`）改为从 `prd-example` 用 `export-prd.sh` 导出，`sample-*.md` 删除，订单系统的文字只保留一份

### 入参要求
- 骨架不写任何业务内容，填写说明本身就是 `[待填]` 后面的文字
- 样例里不允许出现 `[待填]`
- 样例的原型改动后，按顺序重跑 `capture.mjs`、`annotate.mjs`，再重新导出样张

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 骨架目录 | 路径 | 是 | `templates/prd-template/` |
| 样例目录 | 路径 | 是 | `templates/prd-example/` |

### 返回
- 回归测试：样例通过 `check.sh` 全部检查
- 回归测试：骨架运行 `check.sh` 只报 `[待填]` 残留这一类错误，报出其它类别即失败

## 功能四：`[待填]` 残留检查

### 功能描述
`check.sh` 扫描 PRD 根目录下全部 `.md` 与 `.html`（跳过导出目录），出现 `[待填]` 即报，给出文件与行号。拦的是"复制了骨架没填完就交付"：结构检查全绿不代表内容已经写了。

### 入参要求
- 标记固定为半角方括号加"待填"两字，与补文档用的 `[已实现]` 等来源标记、未确认数值用的"待确认"含义不同，互不替代
- 只扫 PRD 根目录，不扫规范文档本身

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| PRD 根目录 | 路径 | 是 | 同 check.sh 的扫描范围 |

### 返回
- 每处残留一条 `[FAIL]`，含文件路径与行号
- 无残留时该项不输出错误

## 功能五：产品形态与截图视口

### 功能描述
原型的界面覆盖要求按产品形态区分，形态在提问阶段问清，记进 `product.md`，由 `check.sh` 校验截图是否与形态一致。

**形态声明**：`product.md` 固定一节，两行：

```markdown
## 产品形态
- 形态：后台管理系统
- 移动端适配：否
```

| 字段 | 取值 |
| --- | --- |
| 形态 | `后台管理系统` / `Web 应用` / `App` / `小程序`，产品同时有多种形态时用顿号分隔，如 `后台管理系统、小程序` |
| 移动端适配 | `是` / `否`；形态只含 `App` 或 `小程序` 时写 `不适用` |

**覆盖表**：`prototype.md` 按四种形态各给一张界面类型覆盖表，形态有多种时每种都要覆盖。

| 形态 | 界面类型 |
| --- | --- |
| 后台管理系统 | 列表页、详情页、表单页、看板页、弹窗、空态与异常（沿用现表） |
| Web 应用 | 入口页、登录注册、核心功能页、个人中心、弹窗、空态与异常（含未登录、无权限） |
| App | 启动与引导、登录、Tab 主页面、列表与详情、表单、底部弹层、系统权限、空态与异常（含无网络） |
| 小程序 | App 的全部类型去掉启动与引导，再加授权弹窗、胶囊避让、分享卡片 |

**提问**：`charles-new-product` 第 0 步的"产品形态与边界"一类必须问清形态；形态含 `后台管理系统` 或 `Web 应用` 时，追问是否适配移动端。`charles-legacy-prd` 从代码判断形态后向 Charles 确认。

**原型节奏**：原型一次做全，覆盖所选形态的覆盖表与 `tasks.md` 里全部任务的页面，做完再交给 Charles 看，不分批交付半成品。

**截图视口**：截图清单新增 `viewport` 字段。

| 取值 | 视口 | 用途 |
| --- | --- | --- |
| `desktop`（缺省） | 1440 x 900，deviceScaleFactor 2 | 后台与 Web 应用的桌面端 |
| `mobile` | 375 x 812，deviceScaleFactor 3 | App、小程序，以及 Web 的移动端适配 |

- 移动端适配为 `是` 时，两端都逐元素标注：每个桌面截图清单 `<shot>.json` 都要有同页面的 `<shot>-mobile.json`，桌面有 `<shot>.marks.json` 的，手机端也要有 `<shot>-mobile.marks.json`
- `annotate.mjs` 按截图的实际宽度排版，不再按 1440 写死

**校验**：`check.sh` 新增三项。

1. `product.md` 缺少"产品形态"一节，或取值不在上表里
2. 移动端适配为 `是` 时，桌面截图清单缺少对应的 `-mobile` 清单，或手机清单的 `page` 与桌面不同，或桌面有标注清单而手机端没有
3. 形态只含 `App` 或 `小程序` 时，截图清单的 `viewport` 不是 `mobile`

### 入参要求
- 形态与适配是提问阶段的必答项，"未回答"不能按默认值写
- 手机截图清单的命名固定为桌面截图名加 `-mobile` 后缀，校验靠命名配对
- 小程序原型仍是静态 HTML，在手机视口里模拟顶部胶囊区域

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 形态 | 文本 | 是 | 见上表取值，可多选 |
| 移动端适配 | 文本 | 是 | `是` / `否` / `不适用` |
| viewport | 文本 | 否 | 截图清单字段，`desktop` 或 `mobile`，缺省 `desktop` |

### 返回
- 形态声明缺失或取值非法时报出具体行
- 缺少手机端清单时报出对应的桌面清单文件名与应有的手机清单文件名

## 功能六：仓库自检

### 功能描述
`tests/check_structure.sh` 检查本仓自身：skill 完整性、每个 SKILL.md 与五处配置的版本号一致、Markdown 内部链接可达，以及禁用字符扫描。本仓的编码与提交规范内联在 `AGENTS.md`，不引用任何其它 skill。

禁用字符按码点列出，规则文本里同样只写码点，不写字符本身：

| 类别 | 码点 |
| --- | --- |
| 弯引号 | U+2018、U+2019、U+201C、U+201D |
| CJK 角引号 | U+300C 到 U+300F |
| 全角引号 | U+FF02、U+FF07 |
| 破折号与横线 | U+2010 到 U+2015、U+2212、U+FF0D、U+2E3A、U+2E3B |
| Emoji | Emoji 区段 |

### 入参要求
- 扫描范围是 git 跟踪的全部文本文件，按扩展名跳过 png、pdf 等二进制文件
- 需要在代码里判断这些字符时（如断行规则），用 `\u` 转义写，不写字面字符

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 仓库根目录 | 路径 | 是 | 脚本所在仓库，自动定位 |

### 返回
- 命中时每处一条 `[FAIL]`，含文件、行号与码点
- 版本号漂移时报出文件与期望版本

## 功能七：四种工作模式与一键出全部

### 功能描述
使用者的场景固定为四种，每种一个工作流 skill，主规范 `charles-prd-standards` 的场景路由表按这四行写。四种模式都支持"一键出全部"，统一流程写在 `rules/one-shot.md`，各 skill 只写自己的差异。

| 模式 | skill | 判据 | 产出落点 |
| --- | --- | --- | --- |
| 1 第一份 PRD，从 0 生成 | `charles-new-product` | 代码不存在，PRD 不存在 | 复制骨架建 `docs/prd/`，写 `versions/1.0/` |
| 2 项目写完了，PRD 没做 | `charles-legacy-prd` | 代码在跑，PRD 不存在或与代码不符 | 版本号对应线上版本，原型从真实前端复刻（功能十） |
| 3 第二版 PRD | `charles-next-version` | PRD 已有且目标版本已发布或已冻结，要规划下一个版本 | 新建 `versions/<新版本>/` |
| 4 在原有基础上加 PRD | `charles-add-feature` | PRD 已有，目标版本状态为 Development，要往里面加内容 | 追加进现有 `versions/<版本>/` |

**模式 3 必问版本号**。先读 `README.md` 的三个状态，按 versioning 的 major 与 minor 规则给出两个候选（线上 1.0 则候选 1.1 与 2.0），同时接受 0.1 这类使用者自定的号。minor 走 `changes.md` 加必要的 Task 与原型，major 走完整目录。版本号未确认不建目录。

**模式 4 只加不改冻结版**。目标版本在 `README.md` 里是 Production 时拒绝追加，提示走模式 3；是 Development 时追加 REQ、Task、原型页面、截图与标注图，并同步 `scope.md`、`decisions.md`、`notes.md` 的需求确认记录。追加的 REQ 与 Task 编号接在现有编号之后，不复用，不重排。

**一键出全部的统一定义**（`rules/one-shot.md`）：

1. 触发：使用者说"一键出全部"、"全部生成"、"一次出完"或等价表述
2. 先问后写：按所属模式的必问项问完，三种状态（已确认、明确不知道、未回答）逐项自检，有"未回答"不开写
3. 一次产出：所属模式的产物清单一次写全，不分批交付半成品
4. 自检：`check.sh` 全绿，再按 `charles-prd-review` 的清单自评审，改不了的列进交付说明
5. 交付说明：三段式，产出了什么、问出来但按默认写的有哪些、评审发现没改的有哪些

### 入参要求
- 四个工作流 skill 都带 `tools` 与 `templates` 软链，`tests/check_structure.sh` 的自足检查覆盖新 skill
- 模式判定写在主规范的场景路由表，四个 skill 的 description 只写触发条件，互相排他
- 模式 3 与模式 4 复用模式 1 的两轮提问（功能八），不另写一套

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 模式 | 枚举 | 是 | 四种之一，由使用者的场景与 README 版本状态判定 |
| 目标版本号 | 文本 | 模式 3、4 必填 | 模式 3 必问；模式 4 取 Development 状态的版本 |

### 返回
- 模式 3 在版本号确认前不建目录；模式 4 对 Production 版本拒绝并给出模式 3 的指引
- 四种模式的产物都通过 `check.sh` 与评审自检后一次交付

## 功能八：两轮提问与需求确认记录

### 功能描述
产出前的提问分两轮，第二轮是新增的。拦的是三类已经发生的偏差：功能被砍成 MVP、只问产品级不问功能细节、问出来的答案没完整落进文档。

**第一轮：产品级七类必答项**，沿用现有内容。

**第二轮：逐模块功能明细确认**。第一轮答完后，先列出完整的模块与功能清单，再按模块给出明细草案，让使用者逐模块确认或修改：

| 草案内容 | 要写到什么程度 |
| --- | --- |
| 功能清单 | 该模块全部功能，一行一个，不按优先级裁剪 |
| 角色与入口 | 谁能用、从哪进 |
| 字段草案 | 字段名、类型、必填、取值 |
| 状态流转 | 状态枚举与每条流转的触发条件 |
| 边界与异常 | 空、超限、冲突、失败各自的行为与文案 |
| 关键数值 | 阈值、时限、容量，推算的标待确认 |

- 每个模块需要使用者定的点不超过四个，写成带选项与推荐项的问题；其余是草案，使用者只需确认或改
- **功能清单未经使用者确认不开写**，与模式 2 现有的清单确认一致
- **范围不许自砍**：1.0 不等于 MVP，要不要分期、砍哪些是产品取舍，只能由使用者决定；Agent 只能提方案并说明代价

**需求确认记录**。骨架 `notes.md` 固定加一节：

```markdown
## 需求确认记录
| 轮次 | 问题 | 结论 | 落点 |
| --- | --- | --- | --- |
| 1 | 产品形态 | 后台管理系统，不适配移动端 | product.md 产品形态 |
| 2 | 订单作废是否二次确认 | 是，列出单号与总金额 | REQ-1.0-003、Task-001 |
```

- 每条结论写明落到哪条 REQ、哪个 Task 或哪个文件的哪一节
- `check.sh` 新增检查：每个 major 版本的 `notes.md` 必须有"需求确认记录"一节，且至少有一行记录（表头与分隔行之外）
- `charles-prd-review` 新增评审项"确认记录逐条对账"：每条结论都能在落点处找到对应内容，找不到就是答案没落进文档

### 入参要求
- 第二轮按模块分批，每批一个模块，等到回答再问下一个模块
- 使用者说"按你的草案来"算已确认，记录里写明是草案确认
- 模式 2 的第二轮以代码扫描出的功能清单为草案底本，问的是"为什么这么做、哪些是有意为之"

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 模块清单 | 列表 | 是 | 第一轮之后列出的全部模块 |
| 每模块问题数 | 整数 | 是 | 上限四个，超出的转成草案让使用者确认 |

### 返回
- 需求确认记录缺节或无记录时 `check.sh` 报出文件
- 评审对账找不到落点的条目，按问题描述、存在的隐患、解决方案三段输出

## 功能九：标注图完整性检查

### 功能描述
标注图沿用左图右文布局：左边截图加红框与编号角标，右边对应编号的说明栏，整张 SVG 在 PDF 里 `width: 100%` 占满正文宽度。

> 作废：曾改为"上图下文"，SVG 只放截图、说明改成图下的 Markdown 列表。Charles 要的是图里带右侧说明的完整标注图，已恢复原布局。

**高宽比上限**。截图高度不超过宽度的 `MAX_ASPECT = 1.25` 倍，A4 竖版正文区放得下并留出图注。桌面 1440 宽最高 1800px；手机 375 宽的整屏 812px 已超限，手机端一律按区块 `crop`。

| 环节 | 行为 |
| --- | --- |
| `capture.mjs` | 截完量到高宽比超限时打印 `[WARN]`，提示用 `crop` 拆分，截图照常产出 |
| `annotate.mjs` | 高宽比超限直接 `[NG]` 拒绝出图，提示拆分 |
| `check.sh` | 读 `_coords.json` 里每个 shot 的 `w`、`h`，超限报出 shot 名与实际比例 |

**标注覆盖**。每个 shot 里 `kind` 为 `btn`、`field`、`link` 的元素都必须有标注；`menu`、`th`、`kpi`、`box` 不强制。

- 覆盖按 `kind` 加 `txt` 分组：十行表格有十个"详情"链接，标一条即覆盖整组
- 确实不该标的写进标注清单的 `skip`：`{ "el": "全选", "kind": "field", "reason": "行为与表头勾选一致，已在表头标注" }`，`reason` 必填
- `capture.mjs` 的 `kindOf` 调整：`nav`、`aside`、`.sidebar`、`.topbar__nav` 内的链接归为 `menu`，侧边导航不再按 `link` 要求逐页标注
- `annotate.mjs` 出图前算覆盖，漏标的列出 `kind:txt` 并拒绝；`check.sh` 用同样的匹配规则独立复算，防止手改 SVG 绕过

**禁止手画界面**。`check.sh` 新增两项：

1. `tasks.md` 的每个 Task 必须有"### 界面"小节（加进 `REQUIRED_TASK_SECTIONS`），且小节内至少一个 `<!--annotation:xxx-->` 标记块，对应的 `xxx.png` 存在
2. `tasks.md` 里标记块之外不允许出现 `<svg`，出现即报行号。界面图只能由 `annotate.mjs` 生成

### 入参要求
- `MAX_ASPECT`、角标尺寸是 `annotate.mjs` 顶部具名常量，改之前按 174mm 宽算实际字号
- 样例 `templates/prd-example/` 的三张标注图按新布局重新生成，样张 PDF 重新导出
- `check.sh` 的覆盖与高宽比检查依赖 python3，缺失时 `[SKIP]` 并说明

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| `MAX_ASPECT` | 数值 | 是 | 高宽比上限，1.25 |
| `skip[]` | 列表 | 否 | 标注清单里明确不标的元素，每项含 `el`、`kind`、`reason` |
| 必标 kind | 枚举 | 是 | `btn`、`field`、`link` |

### 返回
- 超限截图报出 shot 名、实际高宽与上限
- 漏标元素按 `kind:txt` 列出，`skip` 缺 `reason` 单独报
- 手画 SVG 报出文件与行号，缺标记块的 Task 报出任务编号

## 功能十：模式 2 原型复刻

### 功能描述
项目已在跑时，原型必须与真实项目一模一样，不是另画一套。原型从真实前端源码复刻：同一套布局、文案、按钮、状态标签与页面层级，数据换成 Mock，加上截图 hook。现有"已实现且不打算改的功能不写原型与规格"的规则作废。

**覆盖范围**：真实项目的全部页面与弹窗，含已实现且不打算改的；已实现功能同样写 Task、界面标注图与七字段交互规格，规格内容从代码读出，带 `[已实现]` 标记。

**来源对照表** `prototype/sources.md`，每个原型页面一行：

```markdown
| 原型页面 | 真实源码 | 路由 |
| --- | --- | --- |
| pages/order-list.html | src/views/order/List.vue | /orders |
| pages/order-list.html#deleteModal | src/components/order/DeleteConfirm.vue | 同上 |
```

- `check.sh` 新增检查：`prototype/sources.md` 存在时，`prototype/` 下每个 `.html` 都在表里，表里的源码路径在当前仓库里存在
- 模式 2 的交付闸门要求该表存在，模式 1、3、4 不要求
- `charles-prd-review` 新增评审项：真实页面与原型页面并排核对，差异记进 `notes.md`，是有意简化的写明理由

### 入参要求
- 复刻以源码为准，不以旧设计稿或 README 为准
- 真实前端有组件库时，原型用静态 HTML 与 CSS 还原外观，不引入组件库运行时
- 复刻时去掉真实的接口调用与鉴权，保留四种状态的切换

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 真实前端源码路径 | 路径 | 是 | 第 1 步扫描时确定 |
| `sources.md` | 文件 | 模式 2 必填 | 原型页面到源码与路由的对照 |

### 返回
- 对照表缺页面或源码路径不存在时报出具体行
- 评审对照发现的差异按问题描述、存在的隐患、解决方案三段输出
