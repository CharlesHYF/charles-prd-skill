# PRD 规范模块划分
> 模块职责：定义规则模块各自管什么、校验器与内容评审的分工，以及模板、产品形态与仓库自检的约定
> 负责人：Charles
> 系统模块：skill
> 关联文件：skills/charles-prd-standards/rules/、skills/charles-prd-review/SKILL.md、tools/check.sh、tools/capture.mjs、tools/annotate.mjs、templates/、tests/

## 功能一：规则模块边界

### 功能描述
规范本体按关注点拆成下列模块，每条规则只活在一个模块里。

| 模块 | 管什么 | 不管什么 |
| --- | --- | --- |
| structure | 目录结构、文件职责、prd.md 固定章节、字段定义、需求编号、多仓库场景 | 版本之间的关系 |
| versioning | 版本命名、major 与 minor、冻结规则、Git 对应 | 单个版本内部的文件 |
| prototype | 原型形态、按产品形态的界面覆盖表、截图工具契约、规范豁免、时效性 | 图的画法 |
| diagrams | Mermaid 图的类型与尺寸、界面标注图的截图与标注流程、外部位图来源 | 原型本身的内容 |
| boundaries | 产品文档与实现文档的信息落点、Release Criteria 与工程标准的分界 | 实现侧的任何规则 |
| tasks | 任务编号、六个固定小节、交互规格七字段、流程图要求 | 需求条目本身 |
| writing | 需求句式、可判定性、禁用表达、未确认数值的就地标注 | 文档结构 |
| export | 导出 PDF 的单向关系、两份文档的对外范围、交付记录 | 排版样式细节 |
| collaboration | 工作节奏、分析输出格式、产品取舍的处理 | 文档内容本身 |

### 入参要求
- 新增规则前先判定归属模块，避免同一条规则出现在多处
- 涉及实现侧的规则不写进本仓，写成通用表述交给使用者的项目决定
- 字段定义的 SQL 类型与主键策略是例外：字段表是建表的直接依据，属于产品侧有意规定的内容，写在 structure

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 规则内容 | 文本 | 是 | 待归入的规范条目 |
| 是否可机器校验 | 布尔 | 是 | 决定进 check.sh 还是进评审清单 |

### 返回
- 规则归入唯一模块
- 可校验的规则同时具备 check.sh 检查项与回归测试断言

## 功能二：校验器与评审的分工

### 功能描述
确定性规则由 `tools/check.sh` 拦，内容级矛盾由 `charles-prd-review` 的评审清单人工过。两者不重叠。文档里不写两边的条目数量，以 `check.sh` 的输出与评审清单本身为准。

| 校验器管 | 评审管 |
| --- | --- |
| 必需文件、版本目录命名、版本内必需文档 | 需求之间的矛盾 |
| prd.md 章节完整性与字段类型 | 范围与目标对不上 |
| 需求编号存在且不重复 | Non-goals 与需求冲突 |
| 图的位置与来源 | Release Criteria 无法判定 |
| 界面标注图的截图、坐标、标记块与坐标时效 | 需求编号的引用完整性 |
| 版本状态声明 | 原型与 PRD 不一致，含原型没有覆盖所选形态的界面类型 |
| 任务编号、小节、流程图、交互规格字段、已定义任务不留 data-todo | 文字表达无法判定 |
| 角色交叉引用 | 未解决问题的阻塞性 |
| `[待填]` 残留（功能四） | |
| 产品形态声明、截图视口与移动端配对（功能五） | |

### 入参要求
- 新增检查项时同步更新 `tests/run_tests.sh` 的场景
- 发现某类内容问题反复出现且规则确定时，考虑从评审清单升格为检查项

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| PRD 根目录 | 路径 | 是 | 校验器的扫描范围，缺省 docs/prd |

### 返回
- 结构问题由脚本给出文件与具体位置
- 内容问题由评审按问题描述、存在的隐患、解决方案三段输出

## 功能三：模板与样例

### 功能描述
模板拆成两个目录，一个用来复制，一个用来参照。

| 目录 | 用途 | 内容 |
| --- | --- | --- |
| `templates/prd-template/` | 新产品与新版本的复制起点 | 只有结构与填写说明，所有要填的位置用 `[待填]` 前缀；原型是带截图 hook 的最小壳；不含 diagrams 产物 |
| `templates/prd-example/` | 写法参照，不复制 | 订单系统的完整文档、原型、截图与标注，产品形态为后台管理系统、移动端适配为否 |

- 骨架原型只有一个空页面：状态切换条（Empty / Loading / Success / Error）、角色下拉、四个状态区块，满足 `capture.mjs` 的 hook 契约，不含任何业务内容
- 样例由原 `templates/export/sample-prd.md` 与 `sample-tasks.md` 拆回 `product.md`、`prd.md`、`scope.md`、`tasks.md`，原型与标注沿用现有订单系统
- 样张 PDF（`templates/export/sample-prd.pdf`、`sample-tasks.pdf`）改为从 `prd-example` 用 `export-prd.sh` 导出，`sample-*.md` 删除，订单系统的文字只保留一份

### 入参要求
- 骨架不写任何业务内容，填写说明本身就是 `[待填]` 后面的文字
- 样例里不允许出现 `[待填]`
- 样例的原型改动后，按顺序重跑 `capture.mjs`、`annotate.mjs`，再重新导出样张

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 骨架目录 | 路径 | 是 | `templates/prd-template/` |
| 样例目录 | 路径 | 是 | `templates/prd-example/` |

### 返回
- 回归测试：样例通过 `check.sh` 全部检查
- 回归测试：骨架运行 `check.sh` 只报 `[待填]` 残留这一类错误，报出其它类别即失败

## 功能四：`[待填]` 残留检查

### 功能描述
`check.sh` 扫描 PRD 根目录下全部 `.md` 与 `.html`（跳过导出目录），出现 `[待填]` 即报，给出文件与行号。拦的是"复制了骨架没填完就交付"：结构检查全绿不代表内容已经写了。

### 入参要求
- 标记固定为半角方括号加"待填"两字，与补文档用的 `[已实现]` 等来源标记、未确认数值用的"待确认"含义不同，互不替代
- 只扫 PRD 根目录，不扫规范文档本身

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| PRD 根目录 | 路径 | 是 | 同 check.sh 的扫描范围 |

### 返回
- 每处残留一条 `[FAIL]`，含文件路径与行号
- 无残留时该项不输出错误

## 功能五：产品形态与截图视口

### 功能描述
原型的界面覆盖要求按产品形态区分，形态在提问阶段问清，记进 `product.md`，由 `check.sh` 校验截图是否与形态一致。

**形态声明**：`product.md` 固定一节，两行：

```markdown
## 产品形态
- 形态：后台管理系统
- 移动端适配：否
```

| 字段 | 取值 |
| --- | --- |
| 形态 | `后台管理系统` / `Web 应用` / `App` / `小程序`，产品同时有多种形态时用顿号分隔，如 `后台管理系统、小程序` |
| 移动端适配 | `是` / `否`；形态只含 `App` 或 `小程序` 时写 `不适用` |

**覆盖表**：`prototype.md` 按四种形态各给一张界面类型覆盖表，形态有多种时每种都要覆盖。

| 形态 | 界面类型 |
| --- | --- |
| 后台管理系统 | 列表页、详情页、表单页、看板页、弹窗、空态与异常（沿用现表） |
| Web 应用 | 入口页、登录注册、核心功能页、个人中心、弹窗、空态与异常（含未登录、无权限） |
| App | 启动与引导、登录、Tab 主页面、列表与详情、表单、底部弹层、系统权限、空态与异常（含无网络） |
| 小程序 | App 的全部类型去掉启动与引导，再加授权弹窗、胶囊避让、分享卡片 |

**提问**：`charles-new-product` 第 0 步的"产品形态与边界"一类必须问清形态；形态含 `后台管理系统` 或 `Web 应用` 时，追问是否适配移动端。`charles-legacy-prd` 从代码判断形态后向 Charles 确认。

**原型节奏**：原型一次做全，覆盖所选形态的覆盖表与 `tasks.md` 里全部任务的页面，做完再交给 Charles 看，不分批交付半成品。

**截图视口**：截图清单新增 `viewport` 字段。

| 取值 | 视口 | 用途 |
| --- | --- | --- |
| `desktop`（缺省） | 1440 x 900，deviceScaleFactor 2 | 后台与 Web 应用的桌面端 |
| `mobile` | 375 x 812，deviceScaleFactor 3 | App、小程序，以及 Web 的移动端适配 |

- 移动端适配为 `是` 时，两端都逐元素标注：每个桌面截图清单 `<shot>.json` 都要有同页面的 `<shot>-mobile.json`，桌面有 `<shot>.marks.json` 的，手机端也要有 `<shot>-mobile.marks.json`
- `annotate.mjs` 按截图的实际宽度排版，不再按 1440 写死

**校验**：`check.sh` 新增三项。

1. `product.md` 缺少"产品形态"一节，或取值不在上表里
2. 移动端适配为 `是` 时，桌面截图清单缺少对应的 `-mobile` 清单，或手机清单的 `page` 与桌面不同，或桌面有标注清单而手机端没有
3. 形态只含 `App` 或 `小程序` 时，截图清单的 `viewport` 不是 `mobile`

### 入参要求
- 形态与适配是提问阶段的必答项，"未回答"不能按默认值写
- 手机截图清单的命名固定为桌面截图名加 `-mobile` 后缀，校验靠命名配对
- 小程序原型仍是静态 HTML，在手机视口里模拟顶部胶囊区域

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 形态 | 文本 | 是 | 见上表取值，可多选 |
| 移动端适配 | 文本 | 是 | `是` / `否` / `不适用` |
| viewport | 文本 | 否 | 截图清单字段，`desktop` 或 `mobile`，缺省 `desktop` |

### 返回
- 形态声明缺失或取值非法时报出具体行
- 缺少手机端清单时报出对应的桌面清单文件名与应有的手机清单文件名

## 功能六：仓库自检

### 功能描述
`tests/check_structure.sh` 检查本仓自身：skill 完整性、四个 SKILL.md 与五处配置的版本号一致、Markdown 内部链接可达，以及禁用字符扫描。本仓的编码与提交规范内联在 `AGENTS.md`，不引用任何其它 skill。

禁用字符按码点列出，规则文本里同样只写码点，不写字符本身：

| 类别 | 码点 |
| --- | --- |
| 弯引号 | U+2018、U+2019、U+201C、U+201D |
| CJK 角引号 | U+300C 到 U+300F |
| 全角引号 | U+FF02、U+FF07 |
| 破折号与横线 | U+2010 到 U+2015、U+2212、U+FF0D、U+2E3A、U+2E3B |
| Emoji | Emoji 区段 |

### 入参要求
- 扫描范围是 git 跟踪的全部文本文件，按扩展名跳过 png、pdf 等二进制文件
- 需要在代码里判断这些字符时（如断行规则），用 `\u` 转义写，不写字面字符

### 参数
| 参数 | 类型 | 必填 | 说明 |
| ---- | ---- | ---- | ---- |
| 仓库根目录 | 路径 | 是 | 脚本所在仓库，自动定位 |

### 返回
- 命中时每处一条 `[FAIL]`，含文件、行号与码点
- 版本号漂移时报出文件与期望版本
