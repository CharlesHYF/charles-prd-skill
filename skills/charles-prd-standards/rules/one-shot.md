> 使用者说"一键出全部"、"全部生成"、"一次出完"或等价表述时，四种模式都按本文的流程走。**不是立刻开写**，是先把该问的问完，确认后一次产出全部内容。

## 四种模式
| 模式 | 工作流 | 判据 |
| --- | --- | --- |
| 1 第一份 PRD，从 0 生成 | [charles-prd-new-product](../../charles-prd-new-product/SKILL.md) | 代码不存在，PRD 不存在 |
| 2 项目写完了，PRD 没做 | [charles-prd-legacy](../../charles-prd-legacy/SKILL.md) | 代码在跑，PRD 不存在或与代码不符 |
| 3 第二版 PRD | [charles-prd-next-version](../../charles-prd-next-version/SKILL.md) | PRD 已有，目标版本已发布或已冻结，要规划下一个版本 |
| 4 在原有基础上加 PRD | [charles-prd-add-feature](../../charles-prd-add-feature/SKILL.md) | PRD 已有，目标版本还在 Development，要往里面加内容 |

判定不了时先读 `docs/prd/README.md` 的三个版本状态：没有这个文件走模式 1 或 2，按代码是否存在分；有这个文件，要加的内容属于 Development 版本走模式 4，否则走模式 3。

## 五步
### 1. 先问后写
按所属模式的必问项问完。模式 1、3、4 走两轮提问：第一轮七类产品级必答项，第二轮逐模块功能明细确认，细则见 [charles-prd-new-product](../../charles-prd-new-product/SKILL.md) 第 0 步。模式 2 以代码扫描出的功能清单为底本，问的是为什么这么做、哪些是有意为之。

提问方式固定：交互卡片一次最多四个问题，没有交互卡片就每批最多四个编号问题；每批等到回答再问下一批；每个问题给两到四个选项与推荐项。

### 2. 状态自检
产出任何文件之前，把全部必问项列一遍，逐项标注三种状态之一：

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| 已确认 | 使用者给了明确答案 | 写进文档，不加待确认标记 |
| 明确不知道 | 使用者说了"不清楚"或"按默认写" | 按默认值写并就地标注待确认 |
| 未回答 | 这个问题使用者没有回应过 | **必须重新问，不能开写** |

只要还有一项是"未回答"就停下，明确告诉使用者还有几个问题没有答案，要么回答，要么明确授权"按默认值写，标注待确认"。

### 3. 一次产出
所属模式的产物清单一次写全，不分批交付半成品。每一条已确认的结论都要落进文档，并在该版本 `notes.md` 的"需求确认记录"里记一行：轮次、问题、结论、落点（哪条 REQ、哪个 Task 或哪个文件的哪一节）。

原型一次做全，截图与标注图随原型一起出，`tasks.md` 每个任务的界面小节都有标记块。

### 4. 自检
```bash
bash <skill 目录>/tools/check.sh docs/prd
```

全绿后按 [charles-prd-review](../../charles-prd-review/SKILL.md) 的清单自评审，发现的矛盾直接改掉。需求确认记录逐条对账：每条结论在落点处能找到对应内容，找不到就是答案没落进文档，补上。

### 5. 交付说明
三段，缺一不可：

1. **产出了什么**：按产物清单列文件，带版本目录
2. **按默认写的有哪些**：状态为"明确不知道"的项，以及推算出来的数值，都已在需求条目里就地标注
3. **评审发现没改的有哪些**：自评审里改不了的矛盾，以及需要使用者决定的取舍

## 范围不许自砍
- 1.0 不等于 MVP。功能清单以使用者确认的全量为准，不按"先做核心"自行裁剪
- 要不要分期、砍哪些功能是产品取舍，只能由使用者决定；Agent 可以提分期方案并说明代价，不能替使用者定
- 分期定下来后，砍掉的写进 `scope.md` 的 Later，不是直接消失
