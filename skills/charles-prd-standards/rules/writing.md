> 目标是**第一次接触这个产品的人直接看懂，并且能判断做没做到**。不是写得生动，也不是写得像正式文件。

## 需求描述的句式
固定为 **谁 + 在什么条件下 + 能做什么 + 结果是什么**，缺任何一段都要补上。

- 正确：`REQ-1.0-003 续费日前七天向用户推送提醒，提醒内容包含金额与取消入口`
- 错误：`REQ-1.0-003 优化续费提醒体验` -- 没有条件、没有行为、无法判断做没做到
- 错误：`REQ-1.0-003 系统会自动处理续费提醒` -- 主语是"系统"等于没说，自动是什么时机也没说

## 禁止无法判定的表述
> 判据：**能不能写成一条测试用例？** 写不出来就是没描述清楚。

以下词出现在需求描述里一律改写：

| 禁用 | 改成 |
| --- | --- |
| 优化、提升、改善 | 具体改成什么样，给出前后对比或目标值 |
| 更好地、更方便、更流畅 | 具体的行为变化 |
| 合理、适当、尽量、酌情 | 明确的数值或规则 |
| 一般情况下、通常、原则上 | 写清全部分支，包括例外 |
| 支持相关操作、处理相应逻辑 | 列出具体操作 |
| 视情况而定、根据业务需要 | 定下来，定不下来就放进未解决问题 |

## 禁止产品黑话
> 这类词在行业里流通，但对独立开发者没有信息量，而且掩盖了真正要说的事。

赋能、抓手、闭环、打通、拉齐、对齐颗粒度、心智、种草、沉淀、复用能力、链路、生态位、赛道、破局、降本增效、提效、组合拳、护城河、飞轮、精细化运营、用户教育、心智占领。

**人工复查词**（含义依产品而定，不一定要改）：触达、转化、留存、渗透、承接、消费场景、核心资产。这些在有明确定义时可以用，没定义时先在 `product.md` 里定义。

改写示例：

- 错误：`通过消息触达打通用户全链路，提升续费转化` 
- 正确：`续费日前七天推送提醒，目标是把因遗忘导致的流失从当前的两成降到半成以内`

## 未确认的数值必须就地标注
> 推算出来的默认值和业务确认过的规则，在需求条目里长得一模一样，读的人分不出来。

- **凡是没有业务方确认过的数值，在该条需求里就地标注**，不要只在文末的未解决问题里统一列
- 格式：`REQ-1.0-030 资格有效期 12 个月（待确认，见未解决问题 5）`
- 需要标注的典型：有效期、重试次数、超时时长、题库容量、阈值、频率、时间窗口
- 判据：**这个数字是业务方说的，还是你推出来的？** 推出来的就标
- 不标的后果是开发照着实现、题库照着出，等业务方说换证周期是 24 个月时，代码和内容一起返工

## 禁止零信息表达
- 只复述标题的正文（标题写"核心用户流程"，正文写"这里描述核心用户流程"）一律删除
- 说明来源但不说明约束的句子（"参考竞品做法"、"与后端对齐"）一律删除，真正要写的是约束本身
- 空的章节保留标题写"暂无"，不要写一段没有内容的话充数

## 不做无谓中英混杂
- 需求描述用中文，`REQ-1.0-001` 这类编号与 `Non-goals`、`Release Criteria`、`In Scope` 这类没有稳定中文对应的术语保留英文
- 字段名、接口名、状态值保留原文，如 `nextChargeDate`、`status`
- 不写"这个 feature 的 priority 比较 high"这种

## 一句话一个意思
- 一条需求只描述一件事，出现"同时"、"并且"、"另外"时检查是不是该拆成两条
- 拆开的好处是每条都能独立验证，也能独立作废

## 失效需求的写法
需求作废时标注失效并指向替代，**不删除条目**：

```markdown
- REQ-1.0-005 已失效：原计划支持按标签分组，改为 2.0 的 REQ-2.0-002
```

删除条目会让后面的编号含义发生偏移，引用它的测试用例与实现文档也会失去线索。
