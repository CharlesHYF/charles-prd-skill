> 产品文档与实现文档是两套体系，边界不划清就会出现同一件事写两遍然后各自过期。本节只定产品侧的边界，实现侧的规则由项目自己的编码规范管。

## PRD 与模块文档

| | PRD（`docs/prd/`） | 模块文档（`docs/modules/`） |
| --- | --- | --- |
| 回答什么 | 为什么做、这一版做什么、不做什么 | 这个模块的接口怎么调用 |
| 粒度 | 版本级 | 实现级 |
| 内容 | 需求条目（带编号）、用户流程、成功标准 | 功能描述、入参要求、参数、返回 |
| 谁读 | 回头追溯决策时读 | 开工前读、子 Agent 必读 |

- **功能列表只在 PRD 里出现一次**，模块文档不重复列，只写接口契约
- 模块文档在功能描述里引用需求编号（`实现 REQ-1.0-003`），建立双向追溯
- 两边描述冲突时以 PRD 为准，同时说明模块文档需要更新

## Release Criteria 与工程交付标准
- **PRD 的 Release Criteria 只写产品维度的判据**：核心流程能走通、关键指标达标、目标用户能独立完成主任务
- **工程维度由项目自己的交付标准管**：编译通过、测试实跑全绿、性能达标、规范校验通过
- PRD 里不重复定义工程标准，只写一句指向项目交付标准的说明
- 两套标准并行时，实际执行只会看其中一套，另一套形同虚设

## 字段定义属于产品侧
- 字段表的类型列写 SQL 类型、主键用分布式 ID，是**有意规定的产品侧内容**：字段表是建表的直接依据，类型、长度与取值不在 PRD 里定下来，前后端与测试就没有共同的边界值
- 这是"工程维度由项目自己的规范管"的例外，只覆盖字段表，细则见 [structure](structure.md) 的字段定义

## 决策信息的落点
同一类信息有三个可能的位置，按影响范围分：

| 信息 | 落点 |
| --- | --- |
| 跨版本、不可逆的产品级取舍 | `docs/prd/decisions.md` |
| 单个模块的实现选型与技术权衡 | `docs/modules/<模块>.md` |
| 单次改动的原因 | git commit message |

判据：**这个决定会影响下一个版本吗？** 会就进 `decisions.md`，不会就看它是模块级还是单次改动级。

## 原型代码的规范豁免
- `docs/prd/**/prototype/` 加进项目的规范校验排除清单，不受编码规范约束
- 豁免只覆盖原型目录，`docs/prd/` 下的 Markdown 文档仍要遵守文档规范
- 原型代码不许复制进 `src/`，细则见 [prototype.md](prototype.md)

## 文档语言
- 章节标题用中文
- `Non-goals`、`Release Criteria`、`In Scope`、`Later`、`Out of Scope` 这类没有稳定中文对应的正式术语保留英文
- 不做无谓中英混杂，`What` 写成"是什么"，`Target User` 写成"目标用户"，`Problem` 写成"核心问题"
