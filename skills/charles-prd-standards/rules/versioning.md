> 每个版本目录是一份独立快照，不是可以随时回头改的活文档。

## 目录命名
**版本目录直接写明确版本号，禁止 `current`、`latest`、`new` 这类名字。**

```
versions/
├── 1.0/
├── 1.1/    小改版，可只写 changes.md
├── 2.0/
└── 3.0/
```

不用 current 的理由：它总有一天会对不上，而且从目录名看不出它指哪一版，历史版本也就失去了对照价值。

## major 与 minor

| 类型 | 写法 | 适用场景 |
| --- | --- | --- |
| 1.0 / 2.0 / 3.0 | 完整的 `prd.md` + `scope.md` + `prototype/` | 产品阶段发生明显变化 |
| 1.1 / 1.2 / 2.1 | 可以只保留 `changes.md`，必要时附 `prototype/` | 小功能、体验优化、修正 |

## 发布后冻结
> **版本发布的那一刻，该目录冻结。**

- 冻结后**只允许修正笔误**（错别字、格式、失效链接），不允许改需求内容与行为描述
- 任何行为变更一律开新的 minor 目录，在新目录的 `changes.md` 里写明改了哪些需求编号
- 冻结的目的是让 `versions/1.0/` 始终等于"1.0 上线时的样子"。允许回头改的话，它就变成了第二套版本控制，而且比 git 更不可靠
- 已上线版本发现 PRD 描述与实现不符时，不改旧目录，在新版本的 `changes.md` 里记录这个差异

## 与 Git 的对应
- 版本发布时打 git tag，**tag 名与版本目录名一致**（`1.0` 目录对应 `v1.0` tag）
- 这样 `git show v1.0:docs/prd/versions/1.0/prd.md` 能取到发布当时的原文，与冻结后的目录互为佐证
- 版本目录本身不做分支，它是主干上的目录，不需要独立分支生命周期

## 版本状态
`README.md` 里维护三个状态，同一时刻每个状态最多一个版本：

- **Production**：当前线上版本，目录已冻结
- **Development**：正在开发的版本，目录可自由修改
- **Next**：已规划未开工，通常只有 `prd.md` 的骨架
