> 每个文件只做一件事。判断信息该落在哪里，先查下面的职责表。

## 从骨架开始
- 新产品把 `templates/prd-template/` 复制为 `docs/prd/`；新版本把骨架的 `versions/1.0/` 复制为 `versions/<版本>/`
- 骨架里要填的位置都以 `[待填]` 开头，交付前逐项替换成真实内容；不适用的整节删掉，或写"暂无"
- `check.sh` 会拦下残留的 `[待填]`，Markdown 与原型 HTML 都查
- 写法参照 `templates/prd-example/` 的订单系统样例，不要复制样例再删改

## 文件职责

| 文件 / 目录 | 存什么 | 什么时候更新 |
| --- | --- | --- |
| `README.md` | 版本导航：当前线上版本、正在开发版本、下一版本 | 版本状态变化时 |
| `product.md` | 长期稳定的产品定义：用户、问题、价值、产品形态、角色、产品原则 | 产品方向变化时 |
| `decisions.md` | 跨版本的不可逆决策及理由 | 出现影响较大的取舍时 |
| `versions/<版本>/prd.md` | 这一版为什么做、核心体验、核心需求、成功标准 | 版本规划与开发过程中 |
| `versions/<版本>/scope.md` | In Scope / Later / Out of Scope | 每次范围取舍时 |
| `versions/<版本>/notes.md` | 临时想法、未决事项、待验证问题 | 随手记录 |
| `versions/<版本>/prototype/` | 可点击的产品原型 | 交互变化时 |
| `versions/<版本>/diagrams/` | 原型截图与元素坐标、标注清单，以及**外部导入的位图**与其来源说明 | 界面变化时重跑截图与标注，引入外部素材时补来源 |

> **流程图、架构图、状态图一律用 Mermaid 写在 `prd.md` 与 `tasks.md` 正文里，不单独建文件。** 图是文本，写在正文里读者才看得到、导出的 PDF 里才有。写进 `diagrams/` 独立文件的话，正文没有图、PDF 也没有图，等于白画。细则见 [diagrams](diagrams.md)。

## README.md 只做导航
不写产品内容，只回答"现在有哪些版本、各自什么状态"。

```markdown
# PRD

Production: 1.0
Development: 2.0
Next: 3.0

- 产品定义 -> product.md
- 1.0 -> versions/1.0/
- 2.0 -> versions/2.0/
```

## prd.md 的固定结构
> 章节不增不减。这是标准 PRD 的组织方式：先给全貌再展开细节，每个功能自成一块。

```
版本历史          表格：版本、日期、变更内容、修订人
1. 需求概述        产品背景、本版目标、价值点、涉及系统、风险说明
2. 产品描述        名词解释、整体流程、功能清单
3. 功能需求        按模块分组，每个功能含场景描述、需求条目、字段定义、流程
4. 非功能需求      权限与可见性、数据留存、统计与埋点、安全底线
5. Non-goals       明确不做什么
6. 成功标准        Release Criteria
7. 未解决问题      含影响范围
```

### 为什么按模块分组
需求条目平铺成一长串的话，读者要理解某个功能得自己从几十条里挑出相关的拼起来，评审时也没法按功能讨论。**每个功能一个小节，内含场景、需求、字段、流程四块**，读者看完一节就掌握了这个功能的全部。

### 产品形态是必需的
`product.md` 固定有"产品形态"一节，两行：

```markdown
## 产品形态
- 形态：后台管理系统
- 移动端适配：否
```

- 形态取后台管理系统、Web 应用、App、小程序，多种形态用顿号分隔，如 `后台管理系统、小程序`
- 形态含后台管理系统或 Web 应用时，移动端适配写是或否；只含 App 或小程序时写不适用
- 原型要覆盖哪些界面类型、截图用什么视口都按这一节来，见 [prototype](prototype.md)；`tools/check.sh` 校验取值

### 角色表是必需的
多角色产品的 `product.md` 必须有角色表，三列：角色、职责、可操作范围。**`prd.md` 与 `tasks.md` 里出现的每个角色都必须在这张表里存在**，由 `tools/check.sh` 交叉检查。

这条拦的是文档内部自相矛盾：角色表里写了九个角色，需求条目里却冒出"运营总监 → 采购经理 → 总经理"三级审核，而这三个职位表里根本没有。这类不一致相隔几百行，人工评审很难发现，开发按哪个做都可能错。

### 名词解释是必需的
第一次出现的非通用术语必须进表，写清定义、取值范围、谁定的。领域黑话不解释的话，同一个词在不同人嘴里含义不同，理解偏差会推翻整组需求。

### 字段定义是必需的
涉及数据录入或展示的功能必须配字段表，固定六列：字段名、类型、必填、约束、默认值、说明。没有它开发要自己定长度和校验规则，前后端对不齐，测试也没有边界值可测。不涉及数据的功能可以省略本节。

**类型列写 SQL 类型，不写 `String` / `Enum` / `Array` 这类语言层类型。** PRD 里的字段表是建表的直接依据，写语言层类型等于把类型决策推给开发，每个人转换出来的结果还不一样。

| 场景 | 写什么 | 不要写 |
| --- | --- | --- |
| 字符串 | `VARCHAR(n)`，长度按实际业务定 | `String`，或长度一律 255 |
| 长文本 | `TEXT` | `String` |
| 整数 | `TINYINT` / `INT` / `BIGINT` | `Number` / `Integer` |
| 金额与小数 | `DECIMAL(m,n)` | `FLOAT` / `DOUBLE` / `Decimal`，浮点会丢精度 |
| 布尔 | `TINYINT(1)` | `Boolean` / `BIT` |
| 日期时间 | `DATE` / `DATETIME` / `TIMESTAMP` | `Date` |
| 多值 | `JSON`，或拆成关联表 | `Array`，数据库里没有这个类型 |
| 主键 | `BIGINT`（分布式 ID，应用层生成） | 自增主键 |

**枚举字段禁止用 `ENUM` 类型**，改值要 `ALTER TABLE`，跨库迁移也麻烦。用 `TINYINT` 存编码，**在约束列把全部取值逐个列出来**：

```
| cooperationStatus | TINYINT | 是 | 1 待评估 / 2 合作中 / 3 暂停合作 / 4 已退出 | 1 | 合作状态 |
```

取值含义同时要进名词解释表。长度写进类型里（`VARCHAR(20)`），约束列留给业务约束：唯一性、取值范围、条件必填的触发条件、外键关系、格式要求。

### 非功能需求只写产品侧
权限与可见性、数据留存、统计埋点、安全底线这四类是产品决策。**响应时间、并发量、可用性指标属于工程交付标准**，归项目自己的规范体系，PRD 不写也不重复定义。

### 版本历史与目录
版本历史表放 `prd.md` 开头，记录版本、日期、变更内容、修订人。目录由导出工具从标题层级自动生成，不手写也就不会过期。

如果某个功能写到很长，单独拆到 `features/<功能>.md`，在功能需求章节里留一行指向它。

## 需求编号
> 编号是"需求变更"这一档闸门能落地的前提，没有它就无法定位影响面。

- 第 3 章"功能需求"里的每个需求条目**必须带编号**，格式 `REQ-<版本>-<三位序号>`，如 `REQ-1.0-003`
- 编号一经分配不再复用，需求作废时标注失效而不是删除条目并让后面的往前挪
- 测试用例文档的备注列引用该编号，模块文档在功能描述里引用该编号
- 需求变更时按编号反查受影响的测试用例与模块文档

```markdown
#### 需求条目

- REQ-1.0-001 用户用邮箱与密码登录，连续失败五次锁定十分钟
- REQ-1.0-002 登录成功后返回 accessToken 与 refreshToken
- REQ-1.0-003 已失效：改用短信验证码登录，见 REQ-2.0-001
```

## 什么时候再增加文件
> 目录随复杂度增长，不提前创建空文件。

| 出现的问题 | 再增加什么 |
| --- | --- |
| `prd.md` 太长，某个功能占几百行 | `features/<功能>.md` |
| 未决问题太多 | `open-questions.md` |
| 有大量用户调研 | `research/` |
| 原型 CSS 开始重复 | `prototype/components.css` 与 `tokens.css` |
| 关键决策经常被推翻或忘记 | 把 `decisions.md` 拆成 `decisions/` |

## 多仓库产品
- 单产品单仓库时按上面的结构，`docs/prd/` 放在仓库里
- 产品跨多个仓库时，`product.md` 与 `decisions.md` **只在主仓维护**，其余仓库的 `docs/prd/README.md` 用一行链接指过去，不复制内容
- 复制会导致同一产品在不同仓库描述不一致，这类分歧发现时通常已经晚了
